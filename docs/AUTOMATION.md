# TOMORI APP LAB 自動化マニュアル

プログラミングが初めてでも読めるように書いています。Obsidianにそのまま保存できます。

## 1. 自動化の仕組み

```
アプリ側リポジトリ              一覧サイト (tomori-app-lab)
tomori-xxx-007                  GitHub Actions (1時間ごと)
 ├ app-info.json  ──────────▶   ① リポジトリ一覧を取得 (GitHub API)
 └ GitHub Pagesで公開 ───────▶   ② app-info.json を読む・形式チェック
                                ③ 公開成功の履歴と、公開URLへの実アクセスを確認
                                ④ 前回公開分と比較 ─ 変わらない → 何もしない
                                                    └ 変わった → テスト → ビルド → 公開
```

- 対象は `tomoricot-alt` の公開リポジトリのうち、名前が `tomori-<アプリ名>-<3桁の番号>` のもの。`tomori-app-lab` 自身は対象外です。
- 自動登録データはリポジトリに保存せず、**公開のたびにビルド時に作ります**。コミットしないので、権限が少なく済み、「mainを直接編集しない」ルールとも衝突しません。
- 「前回公開した内容」は、公開サイトの `apps-manifest.json` を読んで比較します。
- APP 001〜006 は `app-info.json` がなかったため、`src/data/curated-apps.json` に手動登録した内容を使います（自動処理は書き換えません）。

## 2. 何が自動になったか

新しいアプリを公開すると、次が**指示なしで**行われます。

- 公開の検出 / 公開状況の確認 / 基本情報の取得
- 一覧カード・アプリ番号・名前・アイコン・カテゴリ・紹介文の追加
- 詳細・使い方ページ（`#/apps/007` など。共通テンプレートで自動生成）
- 公開アプリ数と、50アプリに対する進捗率の更新
- GitHub Pagesへの反映

## 3. 自動確認の頻度

- **1時間に1回**（毎時17分 UTC ＝ 日本時間の毎時17分）。GitHubの混雑で数十分遅れることがあります。
- `main` へのマージ時、および手動実行（後述）でも動きます。
- 変更がない回は、数十秒で終わり、ビルドも公開もしません。

## 4. AIトークンを消費しない理由

確認から公開までの処理は、普通のプログラム（Node.js）と GitHub API だけでできています。
Claude Code・ChatGPT・各種AI APIは**呼び出していません**（コード内にも該当する設定はありません）。
アプリの説明文・使い方は、開発時にClaude Codeが `app-info.json` に書いたものを**読むだけ**です。情報が足りないアプリは、AIで推測せず**保留**します。
Claude Codeを使うのは、新しいアプリの開発や、この仕組みの修正のときだけです。

## 5. 無料で運用できる条件

- リポジトリが **Public**（公開）であること。公開リポジトリのGitHub ActionsとPagesは無料です。
- GitHubの標準機能（`GITHUB_TOKEN`、Actions、Pages）だけを使い、個人アクセストークン（PAT）は不要です。
- 有料API・外部サーバー・データベースは使っていません。
- 注意: リポジトリを**非公開**にすると、Actionsの無料枠（月2,000分）やPagesの制限に関わります。Publicのまま運用してください。
- GitHubの仕様: **60日間リポジトリに動きがないと、定期実行が自動で止まります**（6章・9章参照）。

## 6. 新しいアプリを追加する流れ

1. アプリ用リポジトリを `tomori-<名前>-<番号>`（例 `tomori-focus-007`）で作る。
2. Claude Codeに依頼する。**短い指示でOK**です。例:
   > tomoricot-alt/tomori-app-lab の `templates/app-template` を使って、APP 007「○○」を作って。内容は…（アプリの企画だけ書く）
   > （テンプレートの `CLAUDE.md` に共通ルールが入っているので、長い指示は不要です）
3. Claude Codeが、アプリ本体と一緒に `app-info.json`・README・USER_GUIDE・DEV_REPORT・公開設定を作ります。
4. **（初回のみ）** そのアプリのリポジトリで **Settings → Pages → Build and deployment → Source** を **GitHub Actions** にする。
5. Pull Requestを確認して **Merge pull request** を押す（本人の承認）。
6. 公開が成功すると、**最大1時間後**に一覧サイトへ自動で追加されます。急ぐときは7章の手動実行をします。

`app-info.json` が正しい形式かは、アプリ側のCIで自動チェックされます。手元では `npm run validate:app-info`。
公開済みかどうかは、**GitHub Pagesの公開成功履歴 ＋ 公開URLに実際にアクセスできるか**で判定します（CIが成功しただけでは公開済みにしません）。条件を満たさないアプリは**保留**になり、一覧には載りません。

## 7. GitHub Actionsの確認方法・手動実行

**確認**: リポジトリ `tomori-app-lab` → 上部の **Actions** タブ → 左の **Deploy to GitHub Pages** をクリック。
一覧の最新の行が緑✓なら成功です。行をクリックし、`build` → 下のほうの **Summary（概要）** に「保留中のアプリとその理由」「新しく登録したアプリ」が日本語で表示されます。

**手動実行**: Actions → **Deploy to GitHub Pages** → 右側の **Run workflow** ボタン → 緑の **Run workflow**。
（手動実行は、変更がなくても必ず公開します。）

## 8. 自動更新が失敗したとき

| 症状 | 原因の例 | 対応 |
| --- | --- | --- |
| 実行が赤✗ | テスト・ビルドのエラー | 行をクリックし、赤くなったステップのログを読む。直し方はClaude Codeにログを貼って依頼 |
| 黄色の警告（⚠️）が出る | GitHub APIの一時的な不調・制限 | **何もしなくてOK**。既存のサイトはそのままで、次の回に再試行します |
| 新アプリが載らない | Summaryの「保留中」に理由が出ています | 理由に従う（`app-info.json` がない／形式エラー／Pagesの公開が未成功／公開URLにアクセスできない／番号の重複） |
| 載っていたアプリが消えた | リポジトリを削除・非公開にした | 意図しない場合はリポジトリを公開状態に戻す |

安全設計: 取得に失敗しても、**前回掲載した内容を維持**します。問題のあるアプリだけが保留になり、ほかのアプリは影響を受けません。公開（デプロイ）は、テストとビルドが成功したときだけ行われます。

## 9. 定期実行が無効化されたとき

GitHubは、リポジトリに60日間動きがないと定期実行を止めます（Actions画面に「This scheduled workflow is disabled because there hasn't been activity…」と表示）。
復旧: **Actions** → **Deploy to GitHub Pages** → 黄色いバナーの **Enable workflow** をクリック。以後、再び1時間ごとに動きます。
一覧サイト自体が動き続けていれば（アプリの追加・手動実行・READMEの修正など）、通常は止まりません。

## 10. 将来的に50アプリへ増やす方法

- 何も変更しなくて大丈夫です。番号 `001`〜`999` のアプリを自動で登録できます。
- 進捗率の分母（50）は `src/lib/registry.ts` の `GOAL_COUNT` で変更できます。
- 50個を超えても、詳細ページは共通テンプレートなので、ページを個別に作る必要はありません。
- 1時間に使うAPIは、アプリ数に関係なく最小限です（アプリ50個でも数百回以下。上限は1時間1,000回）。

## 11. 無人実行の範囲（承認のルール）

初回のPull Requestは本人がマージするまで反映されません。マージ後に無人で動くのは、このワークフロー（検出 → 検証 → 公開）だけです。ワークフローの権限は `contents: read`（読み取り）と、公開に必要な `pages: write` / `id-token: write` のみです。
